# P6-156 — CI: părțile QEMU împărțite după durata fiecărui scenariu

**Scop:** CI-ul trebuie să rămână sub limita de 60 de minute pe parte. Run 45114337749 (os-366 + P6-153/154): părțile
QEMU au luat 50 / 41 / 37 / 41 min, cu „fiecare al patrulea scenariu”; teste-1 avea toate scenariile lungi
(`kronos-gpu-atentie2` 10 min, `kronos-gpu-atentie-placi` 7 min, `kronos-gpu-pas-aur` 5,5 min). Cu încă 2–3 scenarii
lungi, teste-1 ar fi trecut de 60 de minute și CI-ul ar fi fost roșu fără nicio greșeală în cod.

**Pași:**
1. `tools/durate-ci.py` — din jurnalele părților unui run CI (`gh run view <run> --job <job> --log`), durata fiecărui
   scenariu (de la rândul `== scenariu:` la următorul) → `tests/durate-ci.txt`.
2. `tools/shard.py K/N` — împarte scenariile: cel mai lung întâi, fiecare în partea cu totalul cel mai mic (egalitate:
   numărul cel mai mic); un scenariu nou fără durată = mediana. Determinist: fiecare parte CI calculează singură aceeași
   împărțire. `--table N` arată minutele estimate pe parte.
3. `tools/test.sh --shard K/N` folosește `shard.py` (dacă nu merge: ca înainte, fiecare al N-lea).
4. CI: cinci părți QEMU (`teste-1` … `teste-5`) + `stick`.

**Fișiere:** `tools/shard.py`, `tools/durate-ci.py`, `tests/durate-ci.txt`, `tools/test.sh`, `.github/workflows/ci.yml`.

**Test:** `shard.py --table 5` = ~33,8 min pe fiecare parte (149 scenarii, 168,8 min în total); cele 5 părți au
împreună exact cele 149 de scenarii, fără dubluri; `test.sh --shard 2/5 boot log` rulează ambele, `--shard 1/5 boot`
niciunul. CI: toate cele cinci părți verzi, fiecare sub ~40 min.

**Riscuri:** build-ul unui set nou de opțiuni se mută la primul scenariu care îl cere în partea lui (estimare cu ~1 min
abatere). Duratele îmbătrânesc: când o parte trece de ~45 min, se reface `tests/durate-ci.txt` din ultimul run.

**Surse:** jurnalele run-ului 45114337749; algoritmul „cel mai lung întâi” (LPT, Graham 1969) — idee clasică, cod propriu.
