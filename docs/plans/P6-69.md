# P6-69 — Reparația resetului GSP (I8, „eroare hardware 0xbadf5620”) în OS + Release nou (comanda C-96 pct. 2)

## Scop
Testul din 10 nov (`os-276`, hub `rezultate/2026-11-10-workstation-os276/`): I6 și I7 trec, secvențiatorul pornește (C-91 a mers),
dar `i8-gsp-init` se oprește cu „eroare hardware 0xbadf5620”: prima citire HWCFG2 după resetul falcon-ului GSP întoarce
`0xbadf5620`, iar driverul se oprea la primul `0xbadf…`. cyber-gpu a reparat în `2d66deb` (așteptări tolerante, reset ca în RM,
trecere pe falcon după reset, reset în RISC-V la CORE_RESUME, jurnalul fiecărei cereri `secv #…`). OS-ul ia commit-ul și scoate un Release.

## Pași
1. `kernel/Cargo.toml` pe `rev = "2d66deb"` (toate cele 5 crate-uri cyber-gpu), `Cargo.lock`.
2. Verificare `tools/after-gpu.sh` (SHA-ul lui `add64.sm86.sass`) și scenariile GPU care conțin commit-ul.
3. `tools/build.sh`, `tools/test.sh gpu gpu-sim gpu-i6 gpu-scrie gpu-ro gpu-tur kronos-gpu boot shell`.
4. Commit + push pe `main` → CI verde → Release nou; în hub lista scurtă pentru Adrian (aceeași ca la `os-276`, doar Release-ul nou).

## Fișiere
`kernel/Cargo.toml`, `kernel/Cargo.lock`, eventual `tools/after-gpu.sh`, `tests/scenarios.txt`, `docs/TASKS.md`, `docs/STATE.md`.

## Test
Scenariile GPU din QEMU (SIMULARE) trec ca înainte; CI verde (cele trei părți). Pe placă: doar Adrian, cu `gpu lant` + DA.

## Riscuri
- După reset pot apărea alte diferențe placă/simulare la I8 (`CORE_WAIT_FOR_HALT`, `CORE_RESUME`); lanțul se oprește cinstit, iar jurnalul arată acum comanda vinovată.
- `falcon::SCRUB_US` crește de la 20 ms la 4 s: în cel mai rău caz o oprire durează câteva secunde în plus, nu se blochează.
