# P6-67 — CI-ul în trei bucăți paralele (testele aproape de limita de 60 de minute)

## Scop
Rularea CI de pe `8bdc91e` (7 nov) a durat **54m51s** din limita de 60 (pasul de teste QEMU singur: ~50 min, 97 de
scenarii). Încă 2–3 scenarii și CI-ul ar pica doar din timp, iar Release-ul n-ar mai ieși. Repo-ul e public (DECIZII
2026-10-23 19:05), deci minutele GitHub Actions sunt gratuite: împărțim lucrul pe trei mașini care rulează în același timp.

## Pași
1. `tools/test.sh --shard K/N`: rulează doar scenariile cu numărul de ordine (1, 2, 3 … în `tests/scenarios.txt`,
   fără comentarii) care dă restul K-1 la împărțirea cu N. Fără `--shard`: ca până acum (toate).
2. `.github/workflows/ci.yml`: jobul `build-and-test` devine o matrice cu trei părți: `teste-1` (`--shard 1/2`),
   `teste-2` (`--shard 2/2`), `stick` (testele pe gazdă: crypto, TLS, JSON, Realtek, Intel + imaginile de stick +
   fișierele de Release). `fail-fast: false` (vedem toate erorile). Release-ul tot doar după ce toate trei sunt verzi.
   Cache separat pe parte (fiecare își păstrează propriile fișiere de build).
3. Limita de 60 de minute rămâne pe fiecare parte.

## Fișiere
`tools/test.sh`, `.github/workflows/ci.yml`, `docs/TASKS.md`, `docs/STATE.md`.

## Test
Local: `tools/test.sh --shard 1/2 boot shell` / `--shard 2/2 boot shell` (fiecare rulează exact unul dintre ele),
`--shard 3/2` refuzat. CI: întâi pe ramura `wip/P6-67-ci`; doar dacă toate trei părțile sunt verzi, în `main`
(atunci se face și Release-ul). Același număr total de scenarii trecute (97 cu internet).

## Riscuri
- Un scenariu care depinde de ce a lăsat altul înainte în `build/` (ar pica doar într-o parte) → se vede pe ramura wip.
- Cache-ul mai mare (trei chei) → GitHub șterge singur cache-urile vechi; nimic nu se pierde, doar un build mai lung.

## Surse
Documentația publică GitHub Actions (`strategy.matrix`, `needs`, `actions/cache`).
